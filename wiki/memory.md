# Agent Memory

This file acts as a persistent memory bank where visiting AI agents document long-term learnings, persistent takeaways, and critical knowledge compiled across sessions.

## Long-term Learnings

### About this wiki
- This repo (`helloallytech.github.io` → **tech.helloally.ai**) is the canonical Ally documentation. It is a **public** GitHub Pages site.
- **Sanitization is a hard rule**: never publish secrets, credentials, IP addresses, internal hostnames/domains, or cloud region details. Architecture, SDLC, deployment, and environment *concepts* are in scope; specific sensitive values are not.
- The site was migrated from Jekyll to LLMWiki. `.nojekyll` is required so raw `.md` files are served to the client-side viewer.
- Never edit `llmwiki/` (upstream engine). Always update `wiki/index.md` (catalog) and `wiki/log.md` when adding pages.
- **`wiki/product/` *was* the product-management half of this wiki** (hub + one page per subsection, deliberately open-ended). Deprecated 2026-08-07 — see the entry below. The pattern is still worth knowing because the rest of the wiki uses it: hub page carries the table, each topic gets its own file, register in the hub *and* `index.md`, log it, don't fold a new topic into an existing page to avoid creating a file.
- The hub distinguishes **subsections** (short, opinionated, holdable-in-your-head rule sets) from **reference pages** (long craft lookups filed under a parent subsection, e.g. `chart-dashboard-principles.md` under Data Visualisation). Keep ingested external material as a reference page and keep the subsection short, rather than letting a 500-line ingest swallow the rule set.
- **Product practice is a precondition, not a reference — but it no longer lives here.** As of 2026-08-07 `wiki/product/` is deprecated and superseded by the external **Stacks** MCP: any task that reaches an implementation plan starts by running `/stacks:planning_context` with a description of the task and citing the chunk titles it used — and, since 2026-08-10, so does any product judgement made later while coding (`contributing/planning-with-stacks.md`). Later that same day the server dropped its search tools, leaving that prompt as the only entry point: **an agent cannot reach the library on its own initiative or enumerate what it holds**, so a session claiming Stacks does or doesn't cover something is making an unfalsifiable claim. Judgement calls are filed into Stacks, not back into the wiki. Trivial mechanical changes are exempt.
- **The `wiki/product/` pages are frozen, not deleted, and the freeze has a reason.** Platform pages cite them by principle number (`platform/analytics-agent.md` alone references Data Visualisation 13 and 27–28 and UI & Interaction 4–5). Renumbering or removing a principle silently breaks those citations, so the pages keep their numbering even though nothing in them is a gate any more.
- **A GitHub App cannot approve its own pull request, and on a classic protected branch there is no exemption that gets a bot around it.** The routing-index fan-out opened a PR per wiki push and armed auto-merge; on the three targets requiring one review it stayed armed forever, and 19 superseded snapshots of the same generated file accumulated in each of `ally-be`, `ally-ai` and `ally-web` over 12 days. `ally-ai-learn`, the only target with no protection, was clean throughout — the asymmetry is what located the cause. Both available exemptions were tried and **both fail, for different reasons**: `bypass_pull_request_allowances` sounds like a review waiver but only means "may push without opening a PR", so `REVIEW_REQUIRED` survives on a PR whose checks are all green and whose branch is current; and pushing direct under that same bypass is refused by the required status check — `GH006 ... Required status check "gitleaks" is expected` — because the check cannot run before the ref moves. **Required status checks gate direct pushes, not just merges.** What closes it is a repository *ruleset* bypass (rulesets, unlike classic protection, can waive required reviews for an actor) or a second App whose only job is approving the first one's PR. Absent either, the durable mitigation is shape, not permission: **force-push one long-lived branch instead of branching per commit**, so a regenerated artefact that supersedes its predecessor can never queue more than one PR. Two rules generalise. **When each run of a job fully supersedes the last, per-run branches are a leak** — reuse one. And **a step whose whole job can fail must never discard the reason**: both merge attempts went to `/dev/null` behind a `::warning::`, which does not fail the job, and that is what bought the pileup 12 days; the `GH006` cause above surfaced within one run of printing the output instead. Auto-merge also never rescues a stale branch — it merges only what is already up to date.

### About the Ally platform
- Ally is a HIPAA-compliant platform for training mental-health counselors: AI simulations, real-time session analysis, and peer review. 7 repos (see [Platform Overview](platform/overview.md)).
- Core data flow: web/mobile → **ally-be** (NestJS) → **ally-ai** (analysis/transcription) + **ally-ai-learn** (LiveKit voice training) via REST/SQS/LiveKit. Details in [Architecture](platform/architecture.md).
- Service-to-service auth uses `X-API-Key`; client auth uses JWT/OTP/Google OAuth; all REST APIs are `/api/v1/`.
- SQS queues bridge services (transcription request/response, learn message-and-event, audio upload), each with a DLQ; LocalStack emulates them locally.
- Runtimes: ally-be Node 24, ally-web Node 22, ally-mobile Node ≥18, ally-ai / ally-ai-learn Python 3.12+.
- Each code repo's `AGENTS.md`/`CLAUDE.md` points here as the source of truth — including at the product practices under `wiki/product/`. Update the wiki when architecture, workflows, environment setup, **or product conventions** change.
- Product-relevant platform facts that keep recurring in product decisions: multi-tenant with permission-based (not role-string) gating; HIPAA/PHI limits what can be shown, exported or compared; the product ships in several Indian languages; and many user-visible numbers are LLM-derived scores over small samples, so sample size and rubric/model version matter whenever they're displayed.
- **LLM-generated SQL is a product surface with a trust boundary, and the boundary belongs in the service that owns the database.** The Analytics Agent's pattern generalises: the language service plans and narrates, the data service decides what is readable and enforces it (allowlist + denied columns + `READ ONLY`/timeout/row-cap), so everything that could expose data stays reviewable in a handful of files and the prompts can change freely. Two rules that came out of building it are now in `product/data-visualisation.md` (27, 28): a run-time-chosen chart must be validated against the actual result before it renders — and "no chart" is a legitimate answer — and a number produced by a generated query must show that query, including when the query was refused.
- **A generated-answer surface needs its non-answers designed.** "Ask me anything" tools fail in four distinct ways (ambiguous question, unanswerable from the data, query refused by policy, query failed to run) and each needs its own screen and severity. Collapsing them into one error state is what makes these tools feel unreliable; a clarifying question rendered as an error teaches readers to distrust the whole tab.

- **Roles are additive, but `GET /users/me` reports one.** ally-be has no `role` column: a role is a `groups` row joined through `user_groups`, and permissions are unioned across all of them. `getMinimalUserInfo` collapses that set to a single `role` by a priority list for legacy clients, which is lossy for anyone holding a platform role next to a tenant one. The response also carries a `roles` array — **gate on `roles`; treat `role` as a legacy hint.** Hoisting a new role into the priority list is usually the wrong fix, because the same field feeds the consumer app: raising a staff-only role above `ADMIN` would silently cost staff-who-are-also-org-admins their org-settings access. (Learned while adding the since-withdrawn `INTERNAL` role.)
- **A value clients send verbatim cannot be strictly validated against a server enum you intend to shrink.** ally-be's auth DTOs checked the client-supplied `allowedRoles` list against `UserRole`, so removing a role 400'd every request from any client not yet redeployed — locking *all* users of that surface out of login, not just holders of the removed role. The list is only ever intersected with the account's real group memberships, so an unknown name admits nobody and is inert: dropping it is strictly better than rejecting the request. The general rule — **be lenient about values that can only ever narrow what a request matches, and strict only about values that widen it** — applies to any enum a released mobile build sends, since that client cannot be redeployed at all. Contract and test case: [Login `allowedRoles`](platform/login-allowed-roles.md).
- **Cloned roles need their grants cloned in every future migration.** The `...SUPER_ADMIN_PERMISSIONS` spreads in `permissions.constants.ts` are TypeScript only. `group_permissions` rows are written once by migration and never recomputed, so a cloned role like `SUPER_DUPER_ADMIN` silently falls behind unless each new SUPER_ADMIN grant is written to it too. A spec asserting the permission sets are equal is cheap and catches the drift; the alternative is a 403 nobody can explain. Role/permission lookups also sit behind a 30-minute Redis cache that raw SQL migrations cannot bust.
- **Deciding "which deployment am I?" from one build-time value beats a second flag.** When the admin console briefly shipped to two mount points (its own origin, and `/admin` on the consumer app), everything — asset URLs, router basename, non-router redirects, the `<base>` tag, the surface check — derived from the Vite `base`, so the mount point and the app's belief about the mount point could not disagree. A separate `VITE_IS_EMBEDDED`-style flag is exactly the thing that gets set wrong in one environment. The second surface has since been withdrawn; the rule stands for the next one.
- **Module-load-time work in a shared module breaks unrelated test suites.** Calling a constants helper at import time in `ally-web/apps/ally-admin-dashboard/src/api/auth.ts` took out nine admin test files that mock `@constants` wholesale — they had no reason to know about the new export. Resolving the same value lazily inside the function that needs it keeps the import side-effect-free. Prefer it for anything read from a barrel.

### About automation that reports on itself

- **A check nobody requires is a check nobody passes.** `master` on `ally-be` and `ally-web` ran six and five CI jobs respectively while requiring exactly **one** of them, so the rest were advisory and a red result merged as easily as a green one. Two pull requests merged with a failing lint-and-typecheck job and put a type error on `master` that the test job cannot see — `ts-jest` does not type-check the whole programme the way the production build does — and **nothing could be released for three hours**, because the build job failed and migration, deploy and the release draft were all skipped. The gap was invisible because the PR page showed five green ticks and one red one, and the red one looked optional. Fixed by requiring every check that gates correctness on both repos and enabling `enforce_admins` — but deliberately NOT the docs guard, which enforces a documentation policy rather than correctness and whose escape is a label rather than a fix; measured across twenty merges it was the only required check that would have blocked work someone had every reason to ship, so it stays advisory and keeps its nag without the standoff; the cost of that is that the emergency override is gone too, so the lift-and-restore command belongs in the runbook rather than in someone's memory.
- **"Not found" and "I did not look far enough" must never share an answer.** The release helper picked the next version by scanning a repo's tags and bumping the highest match — reading **one page** of them. In a repo where three independently-released apps share a tag namespace, the first hundred tags were all one app's, so the scan for another app matched nothing, concluded it had never been released, and proposed a first version for something on 1.88. The version validator rejected it, which is the only reason this was a failed release and not a version number walking backwards. Two lessons, and the second is the general one: paginate anything that filters server-side data client-side; and when an empty result can mean either "there is none" or "I stopped early", make the code prove which before it acts — only a short final page proves the whole list was seen.
- **A stored verdict outlives the thing it described.** A run's failure was written onto its session and cleared only by the next run, so a session that could not dispatch another — over budget, parked on a question, blocked on a dead credential — displayed that failure for ever. The same shape appeared four more times in one system: CI failures keyed to a commit that had since been superseded, a release marked failed that a person had since shipped by hand, a phase rail frozen where an agent stopped, and a banner advising a retry of work that was already merged. Each was individually defensible and collectively the page stated the opposite of the evidence sitting under it. **The repair is always the same: re-test the claim against the evidence on a tick, rather than writing it once and trusting it.** The evidence has to be something that cannot be faked by prose — a green check, a merge, a successful workflow run.
- **Put the correction where the evidence lives, not where the failure happened.** The fix for the stale session verdict was written three times before it worked, and the first two were wrong in the same direction: both sat inside a loop over **open** pull requests. The strongest evidence that work succeeded is that it *merged* — which is exactly what removes a pull request from that loop. So the better the evidence got, the less reachable the code reading it became, and two releases shipped that could never have run. What finally located it was checking whether the code path could execute at all, rather than re-reading the logic; a fix that has not been observed doing its job has not been observed at all.
- **An agent that does not know where its job ends will wait for something that never arrives.** A coding agent fixed a real defect, pushed it, CI went green — and then tried to *wait* for CI to confirm, because nothing told it that CI runs after the run ends. Every waiting mechanism the sandbox offered was refused, so it burned two thirds of its turns idling and then ended its turn without reporting an outcome. The harness cannot distinguish "finished quietly" from "died", so it recorded a failure on a run whose work was already merge-ready, advised retrying finished work, and counted it toward the breaker that stops automatic work. **State the consequence, not just the instruction**: "do not wait" is advice, while "ending your turn without reporting is recorded as a failure even when your work pushed cleanly" is the fact that changes the decision.
- **A guard that refuses in silence is indistinguishable from a system with nothing to do.** One dispatch guard returned early without logging, and a wedged session looked exactly like an idle one for four hours — the scheduled task ran every five minutes and reported "Completed" each time. Its neighbours all logged their refusals; this one had been missed. Conversely a guard that announces on every *refusal* rather than once per *state change* turns a stuck session into a message every five minutes for as long as it stays stuck, which is indefinitely when the thing that is stuck is what would clear it.

### About operating the fleet

- **A Wireguard identity cannot be kept warm on a second host.** The identity *is* the private key, so a standby built by copying the hub's configuration does not back the hub up — it becomes a second host answering as the same peer. A fleet survey found exactly that: two hosts presenting an identical public key on the same tunnel address and port, their peer registries ten entries apart, with only one of them receiving handshakes. Identical public keys on two hosts is the visible symptom; the cause is always a copied private key. Give a standby its own keypair and fail over by moving where clients point. ([Operator Access](repos/infra.md#operator-access))
- **A peer added by hand is a peer that will disappear.** Operator VPN access is owned by a portal that reconciles the hub's interface from its own database. Writing a peer straight onto the live interface works immediately, survives until the next reconcile, and then vanishes — which is far harder to debug than being refused up front.
- **An access portal being down is invisible until someone needs access.** The provisioning portal sat cleanly stopped for two months and was found by hand, not by an alert. Nothing in the fleet watches it; the one metrics exporter present was itself in a failed state. Services that are only touched during onboarding decay silently, so they need an uptime check more than the always-hot ones do, not less.
- **`enabled` is not `running`, and long uptime hides the gap.** A unit stopped cleanly stays stopped: `Restart=on-failure` correctly does not fire, and systemd never marks it failed, so it appears in no failed-units list. The `enabled` flag would have restored it at boot — on hosts that had not rebooted in months, that flag was never exercised. When auditing, list what is *running*, not what is enabled.
- **Inventory group names drift from the machines in them.** A group named for baremetal came to include small cloud instances, while the group's blanket `ansible_user: root` was wrong for a host that only permits the unprivileged user. Both failures surface as a confusing permission error mid-play. Treat a group name as intent, and verify class and connecting user per host.
- **Probe with `command -v`, never by running the tool.** Checking for a container runtime by invoking `lxc` on Ubuntu hits the snap stub and *installs* LXD on a production host. Detection commands must not be able to change the system they are detecting.
- **A health check that cannot fail is worse than none, because it is trusted.** A voice-worker fleet lost its connection to LiveKit and stayed disconnected for 19 hours while four separate signals read green: the orchestrator reported the tasks RUNNING (the process never exits — only an internal task dies), no container health check was configured at all, the service's own `/api/health` returned a hardcoded `ok`, and the CloudWatch active-session metric kept publishing at full rate because it is emitted from a hook that runs regardless of connection state. The only honest signal was the one nobody was watching: whether the worker was still registered on the LiveKit side. Two rules generalise. **Check the dependency, not the process** — for anything whose entire job is to hold a connection, liveness means "still registered", and a static `200` on a different port is theatre. And **a retry budget on a long-lived connection is a liveness setting**: a bounded budget that ends by logging and returning, rather than by exiting, converts a transient outage into a permanent one that only a human can clear. Prefer exhausting into a failing health check the orchestrator can act on, or into process exit, over a dead task inside a live process. Mechanism and the per-port detail: [ally-ai-learn](repos/ally-ai-learn.md).
